Three rules

Accepted means stored: the API answers 202 only after the record is written. Push first, sweep second: events drive the normal path, and a timer only catches what was missed. Never send late: past its deadline a wire waits for a person.

How the record drives the wire

Every decision in the rail is a read or a write of one record. This is what each value means.

What the Sweeper is

A small function that we write, started by a schedule every minute. The schedule is configuration. The function is code, on the order of a couple of hundred lines. It copies no payment data: it reads the to-do list and decides who needs a push.

  1. Only one run at a time. Read the to-do index for wires of this region whose nextActionAt has passed, oldest first.
  2. For each one: pending, put the UETR on the submit queue, unless the queue itself is backed up further than the wire has waited. Outcome not yet delivered, put it on the notify queue. Past its deadline, write FAILED_TECHNICAL and raise the alert.
  3. Before queueing a wire, move its nextActionAt forward with a condition on the value just read. Two runs can never queue the same wire.
  4. If the breaker of this region is open, hold every pending wire and let exactly one through as a probe. When it succeeds, drain the rest at a set rate.
  5. Write a heartbeat. If the evacuation runbook has fenced the other region and named this region to take over, take its waiting wires over at a set pace.

The breaker

One small record per region that says whether OPF can be reached from there: closed, open or probing.

  1. It opens when several different wires in a row have failed. One wire that keeps failing cannot open it.
  2. While it is open, nothing is sent and nothing is written per wire. The API keeps accepting.
  3. Once per interval one wire goes out as a probe, a different wire each time. Success closes the breaker.
  4. If the breaker cannot be read, it counts as open.

What Payment Exchange is told

OutcomeIt means
AcceptedOPF has the wire.
RejectedOPF refused the wire. It was not submitted.
Outcome unknownThe rail could not confirm. The payment is held for a person. It is not retried and not reversed.

"Not sent" is not reported. Nothing reached OPF, so Payment Exchange replays the request later and the wire is sent then. "Outcome unknown" is reported because OPF may already hold the wire: a replay after FIS has forgotten the key, or a restart under a new UETR, would move the money twice.

Every outcome carries a sequence number. The only correction ever sent is from "outcome unknown" to accepted, rejected or not submitted, with a higher number, after a person has checked OPF.

What the relay is

The piece between the table and the queues. One small function per region, so that only one reader sits on the table's stream.

  1. The stream. A setting on the table. DynamoDB then emits an event for every write. A global table has it on in each region.
  2. The relay function. Triggered by the stream. It reads the push marker on the record and sends to the submit queue or the notify queue.
  3. The filter. Only events whose new record carries the marker and belongs to this region reach the function. Everything else is dropped.
  4. The message. Only the UETR is sent, never the record.
  5. If it fails. The relay retries, then gives up on that event so the ones behind it are not blocked. The Sweeper finds the wire two minutes later.

It is a function, not an EventBridge Pipe: one reader routes to both queues with no event bus in between, and the function's retry, batch and failure-destination settings give the control the design needs.

Before go-live

The rail repeats a request with the same key by design, after a crash or an unclear result. FIS must confirm in writing how OPF treats such a repeat, and it must be tested in the FIS sandbox with two repeats arriving together.

Old wires

The API refuses a payment that is too old to send. Finished records are purged after the retention period, but a small marker with the UETR and the final status stays, so a UETR that was ever used is always recognised.

How the two regions agree

The table is a strongly consistent global table: a replica in each region and a witness in a third. A write returns only after a second region has it.

  1. The same UETR cannot be accepted in both regions, even at the same instant.
  2. A claim or a takeover in one region is true in the other at once. Two regions never work one wire.
  3. A wire answered with 202 already exists in a second region.
  4. A region that is cut off cannot write, so it stops by itself.
  5. Takeover of waiting wires is started by the evacuation runbook, which fences the failed region first. It is never started by a timer. Each wire carries an owner epoch that rises at takeover, so a late write from the old owner fails.
